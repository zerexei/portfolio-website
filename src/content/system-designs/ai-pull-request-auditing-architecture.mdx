Generative AI coding tools enable rapid feature creation, shifting engineering effort from writing code to comprehension, validation, and invariant enforcement. When LLMs generate hundreds of lines of plausible TypeScript or Python in seconds, peer review can no longer be a line-by-line syntax sanity check.

Instead, code auditing must elevate to a system-level blast-radius analysis: inspecting multi-tenant boundaries, concurrency reentrancy, idempotency guarantees, and resource cleanup topologies.

## The Shift: From Syntax Review to Invariant Enforcement

When reviewing human-written code, reviewers often catch typos, missing off-by-one bounds, or unhandled nulls. Generative AI tools, however, excel at syntax and common design patterns, but struggle with implicit domain invariants and systemic side effects across microservices.

An AI pull request (PR) may appear perfectly clean, passing type-checkers while silently introducing cross-tenant data leaks or non-idempotent database mutations.

## 1. Tenancy Invariant & Scope Boundaries

The most common failure mode in AI-generated multi-tenant backend handlers is implicit scope loss. An LLM will frequently query by `id` without enforcing the enclosing `tenant_id` context—especially in joined relation queries or indirect mutations.

### The Anti-Pattern

An AI-generated batch update handler might write:

```typescript
// BAD: AI-generated update missing tenant scope on joined entities
export async function updateOrganizationProject(
  ctx: RequestContext,
  projectId: string,
  payload: UpdateProjectDTO,
) {
  // Finds project globally without verifying it belongs to ctx.tenantId
  const project = await db.projects.findUnique({ where: { id: projectId } });
  if (!project) throw new NotFoundError("Project not found");

  return await db.projects.update({
    where: { id: projectId },
    data: { ...payload },
  });
}
```

### The Audit Gate

To enforce tenant isolation deterministically, queries must construct composite compound keys or wrap execution in an explicit tenant-scoped database context manager.

```typescript
// GOOD: Strict multi-tenant compound constraint and explicit context guard
export async function updateOrganizationProject(
  ctx: RequestContext,
  projectId: string,
  payload: UpdateProjectDTO,
) {
  return await db.$transaction(async (tx) => {
    const project = await tx.projects.findFirst({
      where: {
        id: projectId,
        tenantId: ctx.tenantId, // Scoped explicitly to active session context
      },
    });

    if (!project) {
      throw new NotFoundError(`Project ${projectId} not found for workspace.`);
    }

    return await tx.projects.update({
      where: {
        id_tenantId: {
          id: projectId,
          tenantId: ctx.tenantId,
        },
      },
      data: {
        name: payload.name,
        description: payload.description,
        updatedAt: new Date(),
      },
    });
  });
}
```

## 2. Idempotency & Safe Execution Topologies

When AI code handles event ingestion (e.g., Webhook handlers, Kafka message consumers, or SQS task queues), it frequently executes side-effects like payment processing or email dispatch before persisting state changes. If the network drops prior to acknowledge, retries trigger duplicate operations.

### Checklist for Event Consumers

- **Deduplication Check:** Is the incoming `eventId` or `idempotencyKey` checked against Redis or a relational DB using a `SELECT FOR UPDATE` or atomic key insertion before performing work?
- **Side-Effect Ordering:** Are external HTTP requests issued _after_ establishing local state reservation, or wrapped in a transactional outbox pattern?
- **Atomic State Updates:** Does the state transition explicitly assert valid expected states (e.g., `WHERE status = 'PENDING'`)?

```typescript
// Idempotency Pattern with Advisory Lock / Unique Constraints
export async function processWebhookEvent(
  db: DatabaseClient,
  redis: RedisClient,
  event: WebhookPayload,
): Promise<void> {
  const lockKey = `lock:event:${event.id}`;
  const acquired = await redis.set(lockKey, "processing", "NX", "EX", 30);

  if (!acquired) {
    // Retried or concurrent invocation detected; abort processing safely
    return;
  }

  try {
    await db.$transaction(async (tx) => {
      // Record incoming idempotency key atomically
      const existing = await tx.processedEvents.findUnique({
        where: { eventId: event.id },
      });

      if (existing) return;

      await tx.processedEvents.create({
        data: { eventId: event.id, processedAt: new Date() },
      });

      // Perform actual business state transition
      await tx.accounts.update({
        where: { id: event.accountId },
        data: { balance: { increment: event.amount } },
      });
    });
  } finally {
    await redis.del(lockKey);
  }
}
```

## 3. Deterministic Resource Management

Generative AI often forgets to clean up transient resources (file descriptors, database connection pools, memory streams, or Redis locks) when handling early error returns or thrown exceptions.

### Structural Verification Rules

- Every stream opening or lock acquisition must be tightly coupled with a `try ... finally` block.
- Early `return` statements inside a `try` block must guarantee cleanup.

```typescript
// Deterministic Stream & Lock Release Pattern
export async function ExportLargeDataset(
  storage: StorageProvider,
  destinationPath: string,
): Promise<void> {
  const fileHandle = await storage.openWriteStream(destinationPath);

  try {
    const cursor = db.records.findManyCursor();
    for await (const chunk of cursor) {
      const buffer = Buffer.from(JSON.stringify(chunk));
      const canContinue = fileHandle.write(buffer);
      if (!canContinue) {
        await new Promise((resolve) => fileHandle.once("drain", resolve));
      }
    }
  } catch (error) {
    logger.error("Dataset export failed midway, unlinking partial file", {
      error,
    });
    await storage.removeFile(destinationPath).catch(() => {
      /* ignore cleanup errors */
    });
    throw error;
  } finally {
    // Guaranteed execution regardless of early returns or thrown errors
    await fileHandle.close();
  }
}
```

## Summary Protocol for Reviewing AI Pull Requests

When auditing PRs generated with LLM assistance, execute this three-step checklist before looking at syntax:

- **Map the Mutation Graph:** Identify every table, cache key, and external service call being modified. Trace if tenant isolation breaks at any link.
- **Simulate Concurrent Interleavings:** Ask, _"What happens if two requests run this handler simultaneously for the same entity?"_ Verify atomic locking or database-level constraints exist.
- **Trace Fault Topologies:** Ask, _"If line N throws a network error, what state is left behind?"_ Ensure deterministic cleanup and idempotent retries.
