In modern customer engagement and support platforms, hybrid routing is standard: an AI conversational bot handles initial intake, and when intent escalation or sentiment degradation occurs, the ticket is transferred to a human agent.

However, without explicit state ownership protocols, handoffs suffer from **split-brain routing**:
- Both the AI bot and the human agent answer the customer's query simultaneously.
- Customer messages sent during the transfer window are dropped or orphaned.
- Agents claim tickets that have already been resolved or transferred elsewhere.

---

## 1. The State Ownership Dilemma

In a distributed real-time chat architecture, multiple actors interact with the conversation session simultaneously:
1. The customer sending messages over a persistent WebSocket connection.
2. The AI bot worker processing conversational intent.
3. Multiple human agents viewing a live triage queue.

If message routing checks only loose database columns without atomic lease ownership, race conditions occur:

```text
Time t0: Customer asks to speak to an agent.
Time t1: Bot sets status = 'escalated' in DB.
Time t2: Agent 1 clicks "Accept Chat".
Time t3: Customer sends another message ("Are you there?").
Time t4: Bot worker and Agent 1 both process message t3 ❌ Double Response!
```

---

## 2. The Solution: Explicit Finite State Machine (FSM)

A conversation session can only have **one authoritative owner** at any given moment. We model the conversation using an unambiguous finite state machine:

```text
[BOT_ACTIVE] ──(Escalate)──> [HANDOFF_PENDING] ──(Claim Lease)──> [AGENT_ACTIVE] ──(Resolve)──> [CLOSED]
      │                              │                                   │
      └─── Customer Disconnect ──────┴───────────────────────────────────┘
```

### State Definitions
- **`BOT_ACTIVE`**: The AI worker holds the exclusive lease. All inbound messages route to the AI pipeline. Human agent inputs are rejected.
- **`HANDOFF_PENDING`**: AI execution is immediately revoked. The conversation enters a priority queue. Customer messages are appended to a buffer log.
- **`AGENT_ACTIVE`**: A single human agent holds the exclusive session lease (`assigned_agent_id`). The bot worker completely ignores incoming messages.
- **`CLOSED`**: Terminal session state. Subsequent customer messages trigger a fresh conversation session.

## 3. Atomic Handoff via Distributed Locking

To prevent race conditions during ticket handoff, state mutations are guarded by distributed locks in Redis:

```typescript
async function executeAgentHandoff(
  ticketId: string, 
  targetAgentId: string
): Promise<{ success: boolean; reason?: string }> {
  const lockKey = `lock:handoff:${ticketId}`;
  
  // Acquire distributed lock with a 5-second TTL
  const acquired = await redis.set(lockKey, targetAgentId, "NX", "EX", 5);
  if (!acquired) {
    return { success: false, reason: "Handoff mutation in progress by another worker" };
  }

  try {
    // Fetch authoritative state from persistent database
    const ticket = await db.tickets.findUnique({ where: { id: ticketId } });
    
    if (ticket.status !== "HANDOFF_PENDING") {
      return { success: false, reason: `Ticket is not in HANDOFF_PENDING (Current: ${ticket.status})` };
    }

    // Atomic transaction: Update ticket ownership + increment agent capacity counter
    await db.$transaction([
      db.tickets.update({
        where: { id: ticketId },
        data: {
          status: "AGENT_ACTIVE",
          assignedAgentId: targetAgentId,
          handoffCompletedAt: new Date()
        }
      }),
      db.agentCapacity.incrementActiveCount(targetAgentId)
    ]);

    // Update fast Redis cache state
    await redis.hset(`session:${ticketId}`, {
      status: "AGENT_ACTIVE",
      owner: targetAgentId
    });

    // Notify connected WebSocket nodes to route live traffic
    await pubsub.publish(`ticket:${ticketId}`, {
      type: "OWNERSHIP_TRANSFERRED",
      newOwner: targetAgentId,
      timestamp: Date.now()
    });

    return { success: true };
  } finally {
    // Release lock only if we own it
    const script = `
      if redis.call("get", KEYS[1]) == ARGV[1] then
        return redis.call("del", KEYS[1])
      else
        return 0
      end
    `;
    await redis.eval(script, 1, lockKey, targetAgentId);
  }
}
```

---

## 4. Buffer-and-Replay Message Routing

When a conversation transitions into `HANDOFF_PENDING`, incoming customer messages must not be dropped while waiting for an agent:

1. Messages arriving during `HANDOFF_PENDING` are appended to the monotonic database log with sequence IDs.
2. The WebSocket gateway sends an immediate acknowledgment frame to the customer UI: `status: "queued"`.
3. As soon as `executeAgentHandoff()` succeeds, the system flushes the unread message buffer directly to the assigned agent's workspace socket, ensuring zero loss of customer context.

Explicit state ownership combined with atomic distributed locking eliminates split-brain routing and guarantees seamless customer transitions.
