In high-concurrency reservation systems (consultations, meeting spaces, or healthcare appointments), the "double booking" problem is a classic **Time-of-Check to Time-of-Use (TOCTOU)** race condition.

When two clients request the exact same slot at the same millisecond, naive implementations read availability concurrently, observe that the slot is open, and write two conflicting reservations—overselling inventory and breaking system integrity.

---

## 1. The Flawed Check-then-Write Pattern

The intuitive but broken implementation looks like this:

```text
Request A: SELECT availability (returns 0 reservations) ──┐
Request B: SELECT availability (returns 0 reservations) ──┼──> Both see open slot
Request A: INSERT INTO reservations (slot_id, user_id)   ──┤
Request B: INSERT INTO reservations (slot_id, user_id)   ──┘──> Both write ❌ Double Booking!
```

### Why Application-Level Checks Fail
Under high concurrent traffic, both requests execute the availability check within the same database snapshot. Because neither transaction has modified state yet, both checks succeed, and both commits write conflicting rows.

---

## 2. Multi-Layered Concurrency Safety Architecture

To guarantee zero double-bookings with sub-100ms response times, the architecture enforces three complementary layers of defense:

### Layer 1: Ingress Idempotency (Absorbing Client Retries)
When a user double-clicks the "Confirm Booking" button or a mobile connection drops and retries, the backend must not process a second reservation.

1. The client sends a header: `Idempotency-Key: uuid-v4`.
2. The API gateway attempts an atomic lock in Redis:
   ```typescript
   const key = `idempotency:booking:${idempotencyKey}`;
   const acquired = await redis.set(key, JSON.stringify({ status: "IN_FLIGHT" }), "NX", "EX", 120);
   
   if (!acquired) {
     const cached = await redis.get(key);
     if (cached && JSON.parse(cached).status === "COMPLETED") {
       return res.status(200).json(JSON.parse(cached).response);
     }
     return res.status(409).json({ error: "Operation currently in progress" });
   }
   ```
3. Once the database transaction commits, the Redis key stores the completed result payload for 24 hours.

---

### Layer 2: Transactional Row-Level Locking (`SELECT FOR UPDATE`)
Inside the database boundary, availability checks and allocation writes are bound into an isolated ACID transaction serialized with a row lock:

```sql
BEGIN;

-- 1. Exclusively lock the slot row; concurrent requests block here
SELECT id, status, provider_id 
FROM schedule_slots 
WHERE id = :slot_id 
FOR UPDATE;

-- 2. Verify that the slot is currently available under lock
SELECT COUNT(*) 
FROM bookings 
WHERE slot_id = :slot_id AND status = 'confirmed';

-- 3. If count == 0, insert reservation
INSERT INTO bookings (slot_id, user_id, status, created_at)
VALUES (:slot_id, :user_id, 'confirmed', NOW());

-- 4. Mark slot inventory as booked
UPDATE schedule_slots 
SET status = 'booked' 
WHERE id = :slot_id;

COMMIT;
```

With `FOR UPDATE`:
- Transaction 1 acquires the exclusive lock on slot 10.
- Transaction 2 blocks at `SELECT ... FOR UPDATE` until Transaction 1 commits or rolls back.
- When Transaction 2 unblocks, it reads the freshly committed state (`status = 'booked'`), detects the conflict, rolls back cleanly, and returns an immediate `409 Conflict`.

---

### Layer 3: Database Unique Exclusion Constraints (The Ironclad Backstop)
Application code changes, developers make mistakes, and distributed locks can expire. The final and non-negotiable safeguard is an explicit database engine constraint:

```sql
ALTER TABLE bookings 
ADD CONSTRAINT unique_active_slot_booking 
UNIQUE (slot_id, status);
```

For systems supporting flexible interval durations, use PostgreSQL temporal exclusion constraints:

```sql
ALTER TABLE appointments 
ADD CONSTRAINT exclude_overlapping_appointments
EXCLUDE USING gist (
    provider_id WITH =,
    tstzrange(start_time, end_time, '[)') WITH &&
) WHERE (status = 'confirmed');
```

Even if application-level locking is somehow bypassed, the database engine aborts conflicting writes with a unique violation code (`23505`), which the backend catches and translates to a graceful error.

---

## 3. Key Takeaways & Guarantees

- **Guaranteed Concurrency Isolation**: Serialized row locks eliminate race windows without distributed lock complexity.
- **Fail-Safe Invariants**: Database-level unique exclusion constraints guarantee that physical inventory can never be oversold.
- **Idempotent Ingestion**: Absorbs network retries and duplicate user actions at the edge, returning cached responses with zero extra database queries.
